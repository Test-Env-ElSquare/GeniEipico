# Overview data sources

Only `/v1/ui/overview` and its child routes changed. Existing routes and the
`success/data/meta/error/ts` envelope remain. Other UI pages retain their services.

Architecture: `UiController` → `IOverviewService` → `IOverviewRepository` /
`IOverviewLiveProvider`. Customer identity comes from the token; factory and line
access is checked before calculation queries. Existing JWT validation remains in force.

## Filters and sources

Use `FactoryId`, optional `LineId`, and `Duration` (0 current, 1 previous shift,
2 day, 3 week, 4 month, 5 custom with factory-local `From` and `To` without a zone suffix).
Explicit zoned timestamps are also accepted as absolute instants. Internal event
queries still use UTC; chart labels and response periods use factory-local time.

- Duration 0 requires an explicit factory. All plants returns empty measurements.
- Eipico live time is configured in `Overview:Eipico` with offset +3.
- Current shift-level data comes exclusively from `Analytics.VW_EipicoOee`, scoped to
  authorized lines and the current shift. Missing provider/view returns empty;
  historical tables are never a fallback.
- Hourly production uses `Analytics.VW_EipicoOee_PerHour` for current data and
  `Analytics.OeeSnapshotsPerHour` for history. It never falls back to shift totals.
- Historical shift-level OEE/output comes from `Analytics.OeeSnapshots`, filtering on
  `ShiftDate`, not the time the snapshot was saved. Eipico ShiftDate is local
  UTC+3; API period boundaries are factory-local, with no `Z` suffix.
  Other existing factories retain their configured offset (currently zero).
- No snapshots are generated by these endpoints. Existing data is read only.

| Route suffix after `/v1/ui/overview/` | Duration 0 | Historical |
| --- | --- | --- |
| `kpis` | View OEE components; alarm count null | Snapshots averages + unresolved AlarmEvents in period |
| `oee-trend` | Average hourly-view OEE per clock hour | Average OeeSnapshotsPerHour.OeePct per clock hour |
| `production-output` | Sum hourly-view Count per clock hour, current shift only | Sum OeeSnapshotsPerHour.TotalOutput per clock hour |
| `factories-production` | View Count, grouped by scope | Snapshot TotalOutput, grouped by scope |
| `energy-by-machine` | Empty, no energy view | Existing snapshot EnergyKwh per machine |
| `active-alarms` | Empty, no alarm view | Up to 4 unresolved, unacknowledged scoped AlarmEvents in period |
| `energy-efficiency` | Empty | Empty until formula/source is defined |
| `energy-by-sku` | Empty | Empty until SKU linkage/source is defined |

EnergyReadings is not yet used to invent efficiency or SKU allocations. Its
transformer/line readings cannot by themselves define these calculations.

## Frontend contract

Ratios stay **0–1** for both sources; multiply by 100 for display. No fake defaults.
For example, `kpis` data is:

```json
[{"oee":0.7065,"availability":0.7065,"performance":1,"qualityRate":1,"activeAlarms":null}]
```

Null means unavailable, not zero. Empty charts retain their shape:
`oee-trend`: `{"labels":[],"oee":[]}`;
`production-output`: `{"title":"Production by hour","labels":[],"series":[{"name":"Production by hour","values":[]}]}`.
Other list sections return `[]`. The aggregate `/overview` composes these same sections.

Production and OEE Breakdown (`oee-trend`) buckets are **clock hours**. Labels represent
factory-local starts (`yyyy-MM-dd HH:mm`), so Eipico 08:00 stays 08:00, not 05:00.
Do not apply another timezone conversion in the frontend. KPI ratios are arithmetic averages of non-null
machine/shift readings; production totals are sums. Factories production groups
by factory without a factory filter, by line with FactoryId, and by machine with LineId.

`meta` supplies source names, factory-local periods, `ratioScale: "0_to_1"`,
`timeBasis: "factory_local"`, `granularity: "hour"` for production and OEE breakdown ("mixed" for the
aggregate page, "shift" for other sections), and empty-result reasons such as `select_factory`,
`live_view_not_configured`, `live_view_unavailable`, or `no_data`.

## Deployment and checks

The hourly update adds a new EF entity/configuration/DbSet. No migration was
generated or database changed by this task. Generate/review/apply a migration for
`Analytics.OeeSnapshotsPerHour` before using historical hourly requests:

```powershell
Add-Migration AddOeeSnapshotsPerHour -Project Infrastructure -StartupProject API
Update-Database -Project Infrastructure -StartupProject API
```

Run the supplied Eipico view scripts (`Analytics.VW_EipicoOee` and
`Analytics.VW_EipicoOee_PerHour`) in SSMS. Both views are read-only SQL projections
mapped by the application; the application does not create/alter them. Until the required views exist, live
production returns an empty chart with `live_view_unavailable`.
Verify the view's SELECT permission and that the target customer/factory/line and shift
master data are populated.
New factories require their own registered live provider and applicable local
snapshot-time configuration, not user-supplied SQL view names.

Run `dotnet run --project tests/Overview.RegressionTests` for routing/access tests.
Add `-- --read-live` for opt-in read-only database verification; this does not
start the API or its startup seeding.
Add `-- --verify-hourly-sql` to execute only the new view's SELECT body against
the configured database, without creating the view or table.

## Hourly storage semantics

`OeeSnapshotsPerHour` intentionally has exactly the existing `OeeSnapshot` properties
and SQL types, per request. `ShiftDate` means **local hour start** in this new table;
`ShiftId` identifies its shift. The unique key remains MachineId + ShiftId + ShiftDate.
For example the 08:00 hour stores ShiftDate `2026-09-30 08:00:00`, and 09:00 stores
`2026-09-30 09:00:00` under the same ShiftId. There is no new HourDate column.

Future storage must map HourStartTime -> ShiftDate, Count -> TotalOutput,
Qreject -> RejectedUnits, AVGSpeed -> AverageSpeedRpm, and the OEE components to
their matching Pct properties (no multiplication by 100). Storage automation is
not part of this change. An empty hourly table yields an empty historical chart.

Existing type limitations were preserved, not silently changed: TotalOutput and
RejectedUnits are integers; ratio columns have two decimal places. Any future
writer must explicitly handle fractional counts and ratio precision requirements.

## Live factory snapshot (SignalR)

Connect to `/hubs/scada` with the JWT access token, listen for
`FactorySnapshotUpdated`, then invoke `SubscribeFactorySnapshot(factoryId, lineId)`.
Pass `null` for `lineId` to include every authorized active line in the factory.
The invoke result contains the initial value; subsequent events are sent only when
the value changes. The view is polled every 10 seconds by default through
`ScadaRealtime:FactorySnapshotPollIntervalMilliseconds`; other SCADA subscriptions
keep their existing polling interval. Invoke `UnsubscribeFactorySnapshot()` when leaving the page.

The current-shift source is `Analytics.VW_EipicoOee`. The payload is:

```json
{
  "success": true,
  "data": {
    "runningLines": 3,
    "totalProduction": 18642,
    "rejectRate": 0.018,
    "activeBatches": 0
  },
  "error": null,
  "ts": "2026-10-01T07:28:31Z"
}
```

`runningLines` is the distinct number of view lines having `State = 1`.
`totalProduction` is `SUM(Count)`. `rejectRate` is
`SUM(Qreject) / SUM(Count)` and remains on the 0-to-1 ratio scale; a zero
production total returns a zero rate. `activeBatches` is intentionally zero until
an authoritative batch source is connected. Factory and optional line access are
validated from the authenticated user's claims before the view is read.

## Live factory layout (SignalR)

Listen for `FactoryLayoutUpdated` and invoke
`SubscribeFactoryLayout(factoryId, lineId)`. Pass `null` for `lineId` to return
all authorized active lines. Invoke `UnsubscribeFactoryLayout()` when leaving the
page. The initial result is immediate; the database is then checked every 10
seconds through `ScadaRealtime:FactoryLayoutPollIntervalMilliseconds`.

Lines and machines come from active master data, so items with no current-shift
telemetry remain visible. Machine `count` is `SUM(RealTime.Production.CountDiff)`
within the current factory-local shift. `speed` and `timestamp` come from the
latest production row in that shift. A machine without any row in the current
shift returns `status: "no_data"`, `speed: 0`, `count: 0`, and `timestamp: null`.
A line is `running` when any of its machines is running, `stopped` when it has
shift data but no running machine, and `no_data` when none of its machines has
shift data. Timestamps and shift boundaries are emitted as UTC; the frontend may
format them in local time.

The hourly view preserves SUM(CountDiff), SUM(Qreject), average State availability,
average nonnegative speed, capped Performance using factor 240, and fixed Quality=1
from the supplied shift view. Only the grouping changes to machine/shift/hour.
It includes partial current hours and excludes future signals. It returns only
shifts AFTER the latest stored factory shift in OeeSnapshotsPerHour. The watermark
is calculated per factory, recovering shift start from the stored local hour date
and ShiftId (including overnight hours). An empty table returns all available
shifts up to now; it does not restrict the view to a single next shift. The API
still selects only the current shift from this view for Duration=0.

Snapshot storage must save the entire factory shift (all its machines/hours) in
one transaction. A saved row marks that shift as stored; partial/manual inserts
can hide remaining hours. Keep shift definitions stable for historical ShiftIds.
If the job saves at 19:59 for a shift ending at 20:00, later signals are not included
and the current chart becomes empty until the next shift starts: there is no
fallback to stored history for Duration=0. Prefer saving after the shift ends,
with an explicit ShiftEndTime cutoff and any required ingestion-delay allowance.
No job was created or rescheduled by this change.

Continue mapping HourStartTime (NOT ShiftStartTime) to the new table's ShiftDate.
Hours with no source signals are omitted,
not fabricated as zero. Overnight shifts retain their original start date;
hour labels after midnight use the actual next calendar date.
